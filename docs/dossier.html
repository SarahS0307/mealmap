MealMap

Rezepte, Meal-Prep-Plan und Einkaufsliste in einer Webapp. Dieses Dossier hält fest, was entschieden ist, was gebaut wird und was noch offen liegt.

Kurzfassung

Drei Module, ein Nutzer pro Datenbestand

MealMap hat eine Hauptnavigation aus Rezepte, Plan und Einkaufsliste, dazu eine Einstellungen-Seite. Angemeldet wird sich nur über den Namen, ohne Passwort; jede Entität hängt an einer user_id, die Nutzer sind vollständig voneinander getrennt.

Der rote Faden ist der Kochrhythmus: sonntags kochen, meist zwei Gerichte, die jeweils zweimal mittags gegessen werden. Daraus ergeben sich Portionen, Vorratsbestand und am Ende die Einkaufsliste — jeder automatische Vorschlag muss aber bestätigt werden, bevor er als fest gilt.

Stand & Weiterarbeiten

Alles, was man zum Anknüpfen wissen muss

Dieser Abschnitt ist bewusst redundant: Er fasst zusammen, was an anderer Stelle ausführlicher steht, damit nach einer Unterbrechung ohne Rückfragen weitergearbeitet werden kann.

Wo das Projekt steht

Phase 0 und 1 sind fertig und geprüft. Grundgerüst, Design nach Moodboard, Datenbankschema mit zwölf Tabellen, PHP-API mit acht Endpunkten, Nutzerverwaltung mit Namensabfrage als Zugangsschranke. Als Nächstes: Phase 2 — Rezepte anlegen, Kategorien, Liste, Detailansicht, Bewertung.

Was man über die Architektur wissen muss

Ziel ist Strato Hosting Starter: PHP und MySQL, kein Node. Deshalb erzeugt Next.js einen rein statischen Export, und alle Daten laufen über die PHP-API in api/. Es gibt kein Prisma, kein SQLite, keine Server-Komponenten mit Datenbankzugriff — die Oberfläche spricht ausschließlich über src/lib/api.ts mit dem Server.

Die drei Stolpersteine

1. Lokal liegt die App unter /MealMap, live an der Wurzel. Deshalb setzen preview und bundle basePath unterschiedlich. Den Server-Ordner immer mit npm run bundle bauen, nie mit preview.
2. npm run build nicht starten, während der Entwicklungsserver läuft — beide schreiben nach .next.
3. Nach jeder Änderung muss npm run preview neu laufen, sonst zeigt localhost:8888/MealMap/ den alten Stand.
4. Dateien aus public/ immer über asset() aus src/lib/paths.ts ansprechen. next/image setzt bei abgeschalteter Bildoptimierung kein basePath davor — ein direkter Pfad funktioniert live, bricht aber lokal.

Entscheidungen

Festgelegt am 12.09.2026

Stack
Next.js als statischer Export + PHP-API + MySQL Umgestellt am 12.09.2026, nachdem feststand, dass das Ziel Strato Hosting Starter ist: klassischer Webspace mit PHP und MySQL, aber ohne Node. Next.js erzeugt deshalb reines HTML, CSS und JavaScript; die Daten kommen über eine PHP-API im Ordner /api. Prisma und SQLite sind entfallen — das durchdachte Datenmodell lebt unverändert als api/schema.sql weiter.
Oberfläche
Tailwind CSS + shadcn/ui Mobile-first. Fertige Dialoge, Formulare und Kalender-Bausteine, Optik später anpassbar.
KI-Import
API-Key pro Nutzer, eingebbar in den Einstellungen Ist ein Key hinterlegt, laufen Rezept-Import aus Bild, PDF und Link sowie die Kategorie-Vorschläge über die KI. Ohne Key funktioniert die App vollständig weiter — nur mit manueller Texteingabe und regelbasierten Vorschlägen.
Betrieb
Vorerst lokal, Livegang später manuell Testdaten entstehen ausschließlich über ein Seed-Skript, nie über Migrationen. Die Live-Instanz startet dadurch automatisch mit leerer Datenbank.
Warum ein Server
Rein clientseitig ginge es nicht Getrennte Nutzer, dieselben Daten auf Handy und Rechner, nur hinterlegte Namen, Spam-Schutz — und vor allem der API-Schlüssel, der niemals im Browser landen darf. Die PHP-API gibt ihn nach außen nie zurück, sondern nur die Auskunft, ob einer hinterlegt ist.
Zieladresse
mealplan.sarah-schoenthaler.de Eigene Subdomain bei Strato. Die App liegt damit im Wurzelverzeichnis, die API schlicht unter /api — keine Unterordner-Pfade nötig.
Lokale Umgebung
Zwei Wege, bewusst beide npm run preview baut den Ordner dist/; eine .htaccess im Projektstamm liefert ihn unter localhost:8888/MealMap/ aus — dieselbe Adresse, die Sarah von ihren übrigen Projekten kennt. Daneben bleibt npm run dev für schnelles Arbeiten mit sofortigem Nachladen. Der Preis: Lokal liegt die App im Unterordner /MealMap, live an der Wurzel der Subdomain. Der Pfad steuert deshalb basePath und wird beim Bauen gesetzt — preview mit /MealMap, bundle ohne. Lokaler und Live-Build sind damit nicht mehr identisch; reine Pfadfehler könnten erst auf dem Server auffallen. Beide Varianten wurden gegengeprüft.
Der Ordner zum Hochladen
dist/, erzeugt mit npm run bundle Enthält die gebaute Oberfläche im Wurzelverzeichnis und api/ daneben — genau die Struktur, die auf die Subdomain gehört. Die Zugangsdaten (api/config.php) bleiben bewusst draußen und werden auf dem Server aus der Vorlage angelegt.
Gestaltung
Moodboard von Sarah, umgesetzt als Design-Tokens Moos, Terrakotta, Senfgelb und Creme, dazu Outfit und Work Sans — durchgehend serifenlos. Liegt als Token-Satz in globals.css, nicht verstreut im Code: ein Farbwechsel trifft damit die ganze App auf einmal. In den Einstellungen lässt sich zwischen Hell, Dunkel und Geräteeinstellung wählen.
Entwicklungsserver
Next.js, wahlweise mit BrowserSync-Proxy davor npm run dev startet nur Next auf Port 3000. npm run sync startet zusätzlich BrowserSync auf 3001 — dafür gibt es eine Netzwerk-URL fürs Handy und synchrones Scrollen und Klicken über mehrere Geräte. Next bringt sein Hot Reloading selbst mit, BrowserSync reicht den Websocket per ws: true durch.
Versionsstände
Bewusst auf stabilen Versionen statt auf latest Der latest-Tag von Prisma zeigt derzeit auf einen Release Candidate (8.0.0-rc.13). Als Fundament ist 7.10.0 festgelegt.
Was ins Repo gehört
Alles außer Generiertem, Installiertem und Geheimem Nicht im Repo: node_modules, die erzeugten Ordner .next, out und dist, sowie api/config.php mit den Zugangsdaten. Im Repo bleiben dagegen .env.example und .env.development — beide enthalten keine Geheimnisse und werden auf jedem Rechner gebraucht.
Versionierung
Git liegt vollständig bei Sarah Keine Commits, keine Branches, kein git init von Claude. Nur die .gitignore wird als Datei angelegt.

Arbeitsplan

Acht Phasen, jede einzeln freizugeben

00

Grundgerüst erledigt

Next.js 15 mit TypeScript, Tailwind v4 und shadcn/ui aufgesetzt, .gitignore und .env.example angelegt. (Die zunächst gewählte Anbindung über Prisma und SQLite wurde später durch die PHP-API ersetzt, siehe Entscheidungen.) Basis-Layout mit Hauptnavigation: Kopfzeile am Desktop, feste Leiste am unteren Rand auf dem Handy. Seiten für alle vier Bereiche vorhanden, noch als Platzhalter. Produktions-Build, Typecheck und Lint laufen fehlerfrei durch.

01

Datenmodell & Nutzerverwaltung erledigt

Datenbankschema mit zwölf Tabellen und allen Korrekturen, in MySQL angelegt. PHP-API mit acht durchgetesteten Endpunkten. Nutzerwechsel direkt in der Kopfzeile, nicht nur in den Einstellungen. Umschalter für Hell, Dunkel und Geräteeinstellung. Namensabfrage versperrt die App, solange niemand angemeldet ist; Session per Cookie, Nutzerwechsel und Abmelden über die Einstellungen. API-Schlüssel pro Nutzer hinterlegbar. Seed-Skript getrennt von den Migrationen. Die Zutaten-Normalisierung fasst in der Stichprobe 12 von 12 Schreibweisen korrekt zusammen, ohne Kollisionen.

02

Rezepte, Basis als Nächstes

Rezept per Text anlegen, Kategorien anlegen, umbenennen und löschen inklusive Umzugs-Dialog für betroffene Rezepte. Rezeptliste, Detailansicht, Bearbeiten, Sternebewertung mit Kommentar, Notizfeld, Einfrierbar-Kennzeichen.

03

Rezepte, Erweiterungen geplant

Bild- und PDF-Upload, Webseiten- und Video-Link mit Embed, KI-Import mit Fallback auf manuelle Eingabe, Kategorie-Vorschläge, Kochmodus mit Timern und live skalierbaren Portionen, PDF-Export, Filter und Volltextsuche.

04

Plan, Basis geplant

Datumsweise Ansicht mit den fünf Slots plus Sonstiges-Liste, manuelles Einplanen, Trennung von Koch- und Essenstermin, Marker für Für-wen, Abwesenheit und Einkaufstag. Standardvorbelegung: kein Frühstück zuhause, Mittagessen im Geschäft.

05

Plan, Automatik geplant

Vorrats- und Bestandsübersicht, automatische Mengenskalierung, Vorschlagsmotor nach dem Sonntagsrhythmus mit Resten zuerst. Vorschläge sind gestrichelt dargestellt und werden erst durch Bestätigung fest.

06

Einkaufsliste, Basis geplant

Automatische Generierung aus bestätigten Plan-Einträgen, Zusammenfassung gleicher Zutaten zu einem Posten, anteiliger Abzug beim Entfernen eines Rezepts, frei hinzufügbare manuelle Posten.

07

Einkaufsliste, Feinschliff geplant

Abgleich mit dem Vorrat, Gruppierung nach Supermarktbereichen von Obst & Gemüse bis Tiefkühl, Bereich „zuletzt erledigt“ am Listenende, Haltbarkeitshinweise für einen möglichen zweiten Einkaufstermin.

Durchgezogene Linie heißt freigegeben, gestrichelt heißt geplant — dieselbe Unterscheidung, die die App später zwischen bestätigten Einträgen und Vorschlägen macht.

Heute legt jeder eingegebene Name automatisch einen neuen Nutzer an. Das soll aufhören: Anmelden heißt nachschlagen, nie anlegen. Die vorhandene Tabelle users ist zugleich die Berechtigungsliste — wer dort nicht steht, kommt nicht rein. Gepflegt wird sie ausschließlich von Sarah direkt in der Datenbank (phpMyAdmin), nicht über die Oberfläche.

Umzusetzen: In api/routes/session.php den INSERT-Zweig entfernen und bei unbekanntem Namen mit 403 antworten. Die Felder closed_signup und allowed_names in api/config.php entfallen dabei — sie waren ein früherer, schwächerer Entwurf mit einer Namensliste in der Konfigurationsdatei. Wichtig: Auf einer frischen Instanz muss vorher mindestens ein Nutzer in der Tabelle stehen, sonst sperrt sich die App selbst aus. Lokal erledigt das npm run db:seed, live ein Eintrag über phpMyAdmin.

Zeitpunkt: Sarah hat entschieden, das erst vor dem Livegang umzusetzen. Während der Entwicklung bleibt das Anlegen über die Oberfläche möglich, was beim Bauen der Rezept-Module praktisch ist.

Frühere Einschätzung korrigiert: Zunächst war vermerkt, dass eine geschlossene Liste die Entwicklung blockiert. Das galt für den Entwurf mit Konfigurationsdatei. Mit der users-Tabelle als Liste blockiert technisch nichts — das Seed-Skript liefert den ersten Nutzer.

Spam- und Zugriffsschutz vor dem Livegang

Damit Unbefugte die öffentlich erreichbare Adresse nicht einfach durchprobieren können: Begrenzung der Anmeldeversuche pro Adresse und eine zusätzliche Hürde vor der Namensabfrage. Lässt sich erst in der Live-Umgebung sinnvoll bauen und prüfen.

Am Ende legt Claude einen Ordner auf den Schreibtisch, der alles enthält, was auf den Live-Server hochgeladen wird. Wichtig dabei: MealMap ist kein PHP-Projekt, sondern braucht Node auf dem Server – siehe offener Punkt weiter unten.

Rezepte aus TikTok teilen Phase 3

Ein Video direkt aus TikTok an MealMap weitergeben, statt den Link von Hand zu kopieren. Das Video wird als eingebettete Quelle am Rezept gespeichert, der Inhalt in Textform daneben. Gehört zum Import-Modul und wird zusammen mit Bild, PDF und Webseiten-Link gebaut.

Mehrere Rezepte in einer Quelle Phase 3

Ein Video oder ein PDF enthält oft nicht ein Rezept, sondern drei. Der Import darf deshalb nicht „eine Datei, ein Rezept“ sein: Er muss erkennen, wie viele Rezepte in der Quelle stecken, sie einzeln auftrennen und jedes davon zur Bestätigung vorlegen — mit der Möglichkeit, einzelne zu verwerfen. Das betrifft den Zuschnitt des Imports, nicht nur eine Zusatzfunktion, und ist vor dem Bau von Phase 3 einzuplanen.

Die heutigen drei Kacheln auf der Startseite sind ein Platzhalter. Später soll dort das Hochladen und Verwalten von Rezepten stattfinden — die Startseite wird damit die Arbeitsfläche, an der neue Rezepte hereinkommen. Die Rezeptsammlung unter /rezepte bleibt davon unberührt und dient weiterhin dem Durchsehen, Filtern und Öffnen vorhandener Rezepte. Umsetzbar erst, wenn es Rezepte und einen Import gibt.

Offene Punkte

Zu klären, bevor die jeweilige Phase startet

API-Key liegt im Klartext vor Livegang

Der Key wird serverseitig am Nutzer gespeichert, sonst könnte der Server die Imports nicht ausführen. In der lokalen MySQL-Datenbank ist das unkritisch. Sobald die App online geht, sollte er verschlüsselt abgelegt werden.

Strato: welches Produkt? Antwort nötig

MealMap ist eine Node-Anwendung mit Datenbank, kein statisches HTML und kein PHP. Das klassische Strato-Webhosting (FTP, PHP, MySQL) kann sie deshalb nicht ausführen – es ist auf PHP ausgelegt und gibt keinen Root-Zugriff. Ein Strato V-Server oder Dedicated Server kann es: volle Rechte, Node installierbar, Next.js ausdrücklich unterstützt. Strato empfiehlt dafür ab 4 GB RAM.

Offen ist, welches Produkt vorliegt. Davon hängt ab, wie der Ordner für den Livegang aussieht – und ob gegebenenfalls ein anderer Tarif nötig wird. Sollte nur klassisches Webhosting verfügbar sein, wären die Alternativen: Tarifwechsel bei Strato, ein anderer Anbieter mit Node, oder ein grundsätzlich anderer technischer Ansatz für MealMap.

Projektordner war im Netz lesbar behoben

Über localhost:8888/MealMap/ lieferte Apache den kompletten Quellcode aus — samt .env im Klartext und der ganzen Git-Historie, und das für jeden im selben WLAN. Eine .htaccess im Projektstamm sperrt jetzt versteckte Dateien, Entwicklungsordner und die Verzeichnisauflistung. Die Zugangsdaten der API waren nie betroffen, die waren von Anfang an gesperrt.

npm audit meldet postcss Entscheidung offen

Next 15.5.25 bringt intern eine postcss-Version mit, für die Sicherheitshinweise vorliegen. Betroffen ist die Build-Kette, nicht die laufende App; lokal ist das unkritisch. Bereinigen ließe es sich nur durch den Sprung auf Next 16 — ein Hauptversionswechsel, den ich nicht ungefragt mache. Spätestens vor dem Livegang entscheiden.

Kosten pro Import Phase 3

Jeder Import aus Bild, PDF oder Link verursacht Kosten über den hinterlegten Key. Ich baue eine Anzeige ein, die vor dem Import sagt, dass jetzt die KI benutzt wird.

Zutaten-Normalisierung lag doppelt vor behoben

Nach dem Architekturwechsel gab es die Vereinheitlichung von Zutatennamen zweimal: in TypeScript und in PHP. Zwei Fassungen laufen unweigerlich auseinander, und dann fasst die Einkaufsliste falsch zusammen. Es gibt jetzt nur noch api/lib/ingredients.php; die tote TypeScript-Fassung ist entfernt.

Einheiten ohne saubere Umrechnung Phase 6

„2 Zwiebeln“ und „150 g Zwiebeln“ lassen sich nicht addieren. Die Liste fasst nur zusammen, was dieselbe Einheit hat, und zeigt den Rest als getrennte Posten. Erfahrungsgemäß der Punkt, an dem eine Einkaufsliste unübersichtlich wird.

Haltbarkeitsdaten kommen nicht von allein Phase 7

Für den Hinweis auf einen zweiten Einkaufstermin braucht es pro Zutat eine grobe Haltbarkeit. Ich starte mit einer hinterlegten Liste für gängige Zutaten, die du überschreiben kannst.

Befehle

Auf einem neuen Rechner starten

Projekt aus Git holen, in den Ordner wechseln, dann diese drei Zeilen — mehr ist nicht nötig:

npm install
cp api/config.example.php api/config.php   # Zugangsdaten der Datenbank
npm run db:migrate  # Tabellen in MySQL anlegen
npm run db:seed     # optional: Beispieldaten
npm run preview     # http://localhost:8888/MealMap/

Voraussetzung ist ein laufender MAMP (Apache und MySQL) sowie eine Datenbank namens mealmap. Die .env und api/config.php liegen bewusst nicht im Repo, weil sie Zugangsdaten enthalten — beide haben eine Vorlage daneben.

npm run buildProduktions-Build, prüft zugleich Typen und Lint-Regeln.
npm run db:migrateLegt die Tabellen in MySQL an, aus api/schema.sql. Live stattdessen die Datei über phpMyAdmin einspielen.
npm run db:seedFüllt Beispieldaten ein. Bewusst getrennt vom Schema, damit die Live-Instanz leer startet.

Arbeitsregeln

Für die Zusammenarbeit

  • Git bleibt bei Sarah. Claude führt keine Git- oder GitHub-Befehle aus — auch keine lesenden wie status oder log. Wenn etwas versioniert werden soll, gibt Claude nur Bescheid, was zu tun ist, und schlägt auf Wunsch eine Commit-Nachricht vor. Ausnahme: die .gitignore darf als Datei angelegt und gepflegt werden.
  • Rückfragen in Abfrageform. Offene Fragen kommen als Auswahl mit erklärten Antwortmöglichkeiten, nicht als Fließtext. Routinemäßige Kleinigkeiten entscheidet Claude selbst und sagt kurz Bescheid.
  • Diese beiden Regeln gelten projektübergreifend. Sie stehen in ~/.claude/CLAUDE.md und werden in jeder Claude-Code-Sitzung geladen, unabhängig vom Projektordner.
  • Phase für Phase. Nach jeder Phase wird gestoppt und auf Freigabe gewartet, bevor es weitergeht.
  • Aufträge werden erst auf den Zeitpunkt geprüft. Vor dem Bauen schätzt Claude ein, ob die Umsetzung jetzt schon sinnvoll ist. Wenn nein, wird sie nicht gebaut, sondern hier im Dossier vermerkt – mit Begründung, wann sie fällig wird.
  • Keine Testdaten in Migrationen. Beispieldaten entstehen nur über npm run db:seed, damit die Live-Datenbank leer startet.
  • Dieses Dossier wird mitgeführt. Entscheidungen, Ideen und offene Punkte kommen hier rein, damit nichts im Chatverlauf verschwindet.
