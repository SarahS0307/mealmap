MealMap

Rezepte, Meal-Prep-Plan und Einkaufsliste in einer Webapp. Dieses Dossier hält fest, was entschieden ist, was gebaut wird und was noch offen liegt.

Ordner ~/Sites/MealMap Quelle mealmap-konzept.md Phase 0 bis 5 erledigt Lokal localhost:8888/MealMap

Kurzfassung

Drei Module, ein Nutzer pro Datenbestand

MealMap hat eine Hauptnavigation aus Rezepte, Plan und Einkaufsliste, dazu eine Einstellungen-Seite. Angemeldet wird sich nur über den Namen, ohne Passwort; jede Entität hängt an einer user_id, die Nutzer sind vollständig voneinander getrennt.

Der rote Faden ist das Vorkochen: Kochtermin und Essenstermin stehen getrennt, daraus ergeben sich Portionen, Vorratsbestand und am Ende die Einkaufsliste. Jeder automatische Vorschlag muss bestätigt werden, bevor er als fest gilt.

Welcher Rhythmus dahintersteckt, gibt die App nicht vor. Sarahs eigener — sonntags kochen, zwei Gerichte, jeweils zweimal mittags — stand anfangs fest im Code und ist wieder herausgenommen worden: solche Gewohnheiten sind bei jeder Person anders. Sie stehen jetzt als Freitext in den Einstellungen.

Stand & Weiterarbeiten

Alles, was man zum Anknüpfen wissen muss

Dieser Abschnitt ist bewusst redundant: Er fasst zusammen, was an anderer Stelle ausführlicher steht, damit nach einer Unterbrechung ohne Rückfragen weitergearbeitet werden kann.

Wo das Projekt steht

Phase 0 bis 5 sind fertig und geprüft. Grundgerüst, Design nach Moodboard, Datenbankschema mit zwölf Tabellen, PHP-API mit 35 Endpunkten, Nutzerverwaltung mit Namensabfrage als Zugangsschranke, vollständiges Rezeptmodul mit Kategorien, Bewertung, Kochmodus, Filtern, Druckansicht, Uploads und KI-Import, dazu der Meal-Prep-Plan mit getrenntem Koch- und Essenstermin in zwei Ansichten — Monatskalender für den Überblick, Tagesansicht zum Bearbeiten. Dazu aus Phase 5: der wochenweise Vorschlagsmotor mit „Reste zuerst“, das Einplanen direkt vom Rezept aus, der Vorrat als vierte Hauptseite und die Mengenskalierung beim Kochen. Als Nächstes: Phase 6 — die Einkaufsliste.

Was man über die Architektur wissen muss

Ziel ist Strato Hosting Starter: PHP und MySQL, kein Node. Deshalb erzeugt Next.js einen rein statischen Export, und alle Daten laufen über die PHP-API in api/. Es gibt kein Prisma, kein SQLite, keine Server-Komponenten mit Datenbankzugriff — die Oberfläche spricht ausschließlich über src/lib/api.ts mit dem Server.

Die drei Stolpersteine

1. Lokal liegt die App unter /MealMap, live an der Wurzel. Deshalb setzen preview und bundle basePath unterschiedlich. Den Server-Ordner immer mit npm run bundle bauen, nie mit preview.
2. npm run build nicht starten, während der Entwicklungsserver läuft — beide schreiben nach .next.
3. Nach jeder Änderung muss npm run preview neu laufen, sonst zeigt localhost:8888/MealMap/ den alten Stand.
4. Datumsrechnungen nie zwischen PHP und MySQL mischen, ohne die Zeitzone zu prüfen. PHP läuft ohne Angabe auf UTC, MySQL auf der Systemzeit — das waren hier zwei Stunden Unterschied. api/lib/http.php setzt die Zeitzone jetzt aus der Konfiguration; Fristen werden trotzdem lieber in SQL gerechnet, damit nur eine Uhr im Spiel ist.
5. uploads/ beim Hochladen auf den Server nie mitlöschen — dort liegen Sarahs Bilder und PDFs, und der Ordner entsteht nicht neu.
6. Dateien aus public/ immer über asset() aus src/lib/paths.ts ansprechen. next/image setzt bei abgeschalteter Bildoptimierung kein basePath davor — ein direkter Pfad funktioniert live, bricht aber lokal.

Entscheidungen

Festgelegt am 12.09.2026

Stack
Next.js als statischer Export + PHP-API + MySQL Umgestellt am 12.09.2026, nachdem feststand, dass das Ziel Strato Hosting Starter ist: klassischer Webspace mit PHP und MySQL, aber ohne Node. Next.js erzeugt deshalb reines HTML, CSS und JavaScript; die Daten kommen über eine PHP-API im Ordner /api. Prisma und SQLite sind entfallen — das durchdachte Datenmodell lebt unverändert als api/schema.sql weiter.
Oberfläche
Tailwind CSS + shadcn/ui Mobile-first. Fertige Dialoge, Formulare und Kalender-Bausteine, Optik später anpassbar.
KI-Import
API-Key pro Nutzer, eingebbar in den Einstellungen Ist ein Key hinterlegt, laufen Rezept-Import aus Bild, PDF und Link sowie die Kategorie-Vorschläge über die KI. Ohne Key funktioniert die App vollständig weiter — nur mit manueller Texteingabe und regelbasierten Vorschlägen.
Betrieb
Vorerst lokal, Livegang später manuell Testdaten entstehen ausschließlich über ein Seed-Skript, nie über Migrationen. Die Live-Instanz startet dadurch automatisch mit leerer Datenbank.
Rolle von Next.js
Werkzeug auf dem Entwicklungsrechner, nicht auf dem Server Next.js erzeugt aus dem React-Code fertige HTML-, CSS- und JavaScript-Dateien. Auf Strato landet nur dieses Ergebnis plus die PHP-API — dort läuft kein Node. Next zu entfernen hieße, die komplette Oberfläche in PHP-Templates neu zu schreiben; das Ziel „läuft auf Strato“ ist ohne das bereits erfüllt.
Warum ein Server
Rein clientseitig ginge es nicht Getrennte Nutzer, dieselben Daten auf Handy und Rechner, nur hinterlegte Namen, Spam-Schutz — und vor allem der API-Schlüssel, der niemals im Browser landen darf. Die PHP-API gibt ihn nach außen nie zurück, sondern nur die Auskunft, ob einer hinterlegt ist.
Zieladresse
mealplan.sarah-schoenthaler.de Eigene Subdomain bei Strato. Die App liegt damit im Wurzelverzeichnis, die API schlicht unter /api — keine Unterordner-Pfade nötig.
Lokale Umgebung
Zwei Wege, bewusst beide npm run preview baut den Ordner dist/; eine .htaccess im Projektstamm liefert ihn unter localhost:8888/MealMap/ aus — dieselbe Adresse, die Sarah von ihren übrigen Projekten kennt. Daneben bleibt npm run dev für schnelles Arbeiten mit sofortigem Nachladen. Der Preis: Lokal liegt die App im Unterordner /MealMap, live an der Wurzel der Subdomain. Der Pfad steuert deshalb basePath und wird beim Bauen gesetzt — preview mit /MealMap, bundle ohne. Lokaler und Live-Build sind damit nicht mehr identisch; reine Pfadfehler könnten erst auf dem Server auffallen. Beide Varianten wurden gegengeprüft.
Der Ordner zum Hochladen
dist/, erzeugt mit npm run bundle Enthält die gebaute Oberfläche im Wurzelverzeichnis und api/ daneben — genau die Struktur, die auf die Subdomain gehört. Die Zugangsdaten (api/config.php) bleiben bewusst draußen und werden auf dem Server aus der Vorlage angelegt.
Gestaltung
Moodboard von Sarah, umgesetzt als Design-Tokens Moos, Terrakotta, Senfgelb und Creme, dazu Outfit und Work Sans — durchgehend serifenlos. Liegt als Token-Satz in globals.css, nicht verstreut im Code: ein Farbwechsel trifft damit die ganze App auf einmal. In den Einstellungen lässt sich zwischen Hell, Dunkel und Geräteeinstellung wählen.
Aufruf der KI
Rohes HTTP statt PHP-SDK Der Import ruft die Anthropic-API direkt über cURL auf (api/lib/claude.php, Modell claude-opus-5, strukturierte Ausgabe per JSON-Schema). Ein SDK brächte Composer und einen vendor-Ordner mit — auf Strato wird aber nur hochgeladen, ohne Paketverwaltung. Der Schlüssel gehört dem Nutzer, liegt in der Datenbank und verlässt den Server nie.
Hochgeladene Dateien
Im Ordner uploads/, außerhalb des Bündels Bilder und PDFs liegen bewusst nicht in dist/ — das entsteht bei jedem Bau neu und würde sie mitnehmen. Beim Hochladen auf den Server darf uploads/ nie mitgelöscht werden. Geprüft wird der Dateiinhalt, nicht die Endung; der Dateiname wird neu vergeben.
PDF-Erzeugung
Über den Druckdialog des Browsers, ohne Zusatzpaket Eine Druckvorlage in globals.css blendet alles Bedienbare aus; „Als PDF sichern“ erledigt den Rest. Das setzt den Satz besser als eine JavaScript-Bibliothek und braucht keinen Server — auf dem Webspace gäbe es dafür ohnehin keinen. Markiert wird über data-print="aus" und data-print="nur".
Entwicklungsserver
Next.js, wahlweise mit BrowserSync-Proxy davor npm run watch ist der normale Weg: Es baut bei jeder Änderung neu und lädt die Seite im Browser automatisch nach. BrowserSync läuft dabei als reiner Meldedienst auf Port 3001 — ausgeliefert wird weiterhin von Apache unter localhost:8888/MealMap/, die Seite lädt nur das Melde-Skript nach. Die gewohnte Adresse bleibt damit unverändert. npm run dev (Port 3000) bleibt als Schnellmodus erhalten.
Was ins Repo gehört
Alles außer Generiertem, Installiertem und Geheimem Nicht im Repo: node_modules, die erzeugten Ordner .next, out und dist, sowie api/config.php mit den Zugangsdaten. Im Repo bleiben dagegen .env.example und .env.development — beide enthalten keine Geheimnisse und werden auf jedem Rechner gebraucht.
Persönliche Gewohnheiten
Freitext in den Einstellungen, nichts davon im Code Mittags auswärts, kein Frühstück zuhause, sonntags vorkochen — das stand anfangs fest im Vorschlagsmotor, übernommen aus dem Konzept. Sarah hat es zurückgenommen: solche Regeln sind bei jeder Person anders. Sie stehen jetzt als Freitext an users.habits und gehen beim Vorschlagen an die KI. Die Trennlinie: Tatsachen dürfen in den Code (Wochentage, gesetzliche Feiertage, Ladenschluss — gelten für alle), Gewohnheiten nie. Ohne Text verhält sich der Motor neutral, statt etwas anzunehmen.
Feiertage
Eigene Tabelle im PHP, Bundesland je Nutzer einstellbar Vorgabe ist Baden-Württemberg, änderbar in den Einstellungen. Die sechzehn Länder stehen in api/lib/feiertage.php, die beweglichen Feiertage über die Gaußsche Osterformel — easter_date() aus PHP wäre kürzer, setzt aber die Kalender-Erweiterung voraus, auf die bei Strato kein Verlass ist. Die Tabelle steht nur serverseitig: die Plan-Ausgabe liefert je Tag holiday, isWorkday und canShop mit, damit das Frontend nichts nachbauen muss. Nicht abgebildet sind Feiertage, die nur einzelne Gemeinden betreffen (Augsburger Friedensfest, Mariä Himmelfahrt in Bayern) — die hängen am Ort, nicht am Land.
Versionierung
Git liegt vollständig bei Sarah Keine Commits, keine Branches, kein git init von Claude. Nur die .gitignore wird als Datei angelegt.

Arbeitsplan

Acht Phasen, jede einzeln freizugeben

00

Grundgerüst erledigt

Next.js 15 mit TypeScript, Tailwind v4 und shadcn/ui aufgesetzt, .gitignore und .env.example angelegt. Basis-Layout mit Hauptnavigation: Kopfzeile am Desktop, feste Leiste am unteren Rand auf dem Handy. Seiten für alle vier Bereiche vorhanden, noch als Platzhalter. Produktions-Build, Typecheck und Lint laufen fehlerfrei durch.

01

Datenmodell & Nutzerverwaltung erledigt

Datenbankschema mit zwölf Tabellen und allen Korrekturen, in MySQL angelegt. PHP-API mit acht durchgetesteten Endpunkten. Nutzerwechsel direkt in der Kopfzeile, nicht nur in den Einstellungen. Umschalter für Hell, Dunkel und Geräteeinstellung. Namensabfrage versperrt die App, solange niemand angemeldet ist; Session per Cookie, Nutzerwechsel und Abmelden über die Einstellungen. API-Schlüssel pro Nutzer hinterlegbar. Seed-Skript getrennt von den Migrationen. Die Zutaten-Normalisierung fasst in der Stichprobe 12 von 12 Schreibweisen korrekt zusammen, ohne Kollisionen.

02

Rezepte, Basis erledigt

Rezepte anlegen, bearbeiten und löschen mit Zutaten, Zubereitungsschritten, Notiz, Portionen, Zubereitungszeit und Einfrierbar-Kennzeichen. Liste mit Suche und Kategoriefilter, Detailansicht, Sternebewertung mit Kommentar. Kategorien anlegen, umbenennen und löschen — beim Löschen mit enthaltenen Rezepten fragt die App nach, wohin sie sollen, statt sie stillschweigend zu verlieren.

Dazu ein Ändern-Knopf für Änderungen in Alltagssprache: „2 statt 3 Eier“, „ohne Zwiebeln“, „300 g Mehl“, „Butter durch Öl ersetzen“. Die App zeigt erst, was sie verstanden hat, und schreibt erst nach Bestätigung — direkt ins Rezept, nicht als Notiz daneben (Konzept 4.2). Erkannt werden feste Muster; beliebige Sätze versteht sie erst mit dem KI-Import.

03

Rezepte, Erweiterungen erledigt

In sechs Teilschritten gebaut, damit jeder für sich nutzbar ist:

3a Kochmodus. Schritt-für-Schritt-Ansicht, Timer je Schritt, live umgerechnete Portionen, Bildschirmsperre aus, Blättern per Pfeiltasten. Am Ende ein Schlussbildschirm mit der Einladung, gleich zu bewerten.
3b Filter und Suche. Suche über Titel, Zutaten und Kategorien; kombinierbare Filter für Kategorie, Einfrierbar, Mindestbewertung und Zubereitungszeit. Gefiltert wird auf dem Server.
3c Druckansicht. Drucken-Knopf in der Rezeptansicht, PDF über den Druckdialog des Browsers.
3d Uploads und Einbettungen. Bilder und PDFs bis 12 MB; geprüft wird der Dateiinhalt, nicht die Endung. Bilder hängen am Rezept, das Entfernen löscht auch die Datei. Eine Quelladresse wird als Video oder Link erkannt — YouTube und Vimeo werden eingebettet, TikTok und Instagram als gekennzeichneter Link gezeigt.
3e KI-Import. Rezepte aus Text, Link, Bild oder PDF. Eine Quelle kann mehrere Rezepte enthalten; sie erscheinen einzeln und lassen sich einzeln abwählen. Kategorien werden vorgeschlagen und vorhandenen zugeordnet, statt Doppelungen anzulegen.
3f Startseite als Rezeptaufnahme. Die drei Kacheln sind dem Import gewichen; die Sammlung unter /rezepte blieb unberührt.

Zusätzlich: Papierkorb. Gelöschte Rezepte liegen 30 Tage bereit und lassen sich zurückholen. Abgelaufenes räumt die App beim Zugriff selbst weg, weil es auf klassischem Webspace keine geplanten Aufgaben gibt. Erreichbar am Fuß der Rezeptliste, bewusst nicht in der Hauptnavigation.

04

Plan, Basis erledigt

Datumsweise Ansicht, eine Woche auf einmal, mit den fünf Slots plus Sonstiges. Je Slot sind mehrere Einträge möglich — Suppe und Crêpe nebeneinander, oder für Annika Erbsensuppe und für Sarah und Mama Kartoffelsuppe. Einträge nehmen ein Rezept, freien Text oder Vorratsposten, dazu Portionen und für wen gekocht wird — namentlich Genannte und zusätzlich eine Anzahl weiterer Personen für Besuch ohne Namen. Beides steht getrennt, weil eine Anzahl keine Liste ist; später wird aus den Namen eine Auswahl aus dem Haushalt, die Anzahl bleibt daneben. Kochtermin und Essenstermin stehen getrennt — sonntags kochen, dienstags essen; der Kochtag erscheint auch beim Kochtermin selbst, mit Hinweis, für wann gekocht wird. Marker für Abwesenheit und Einkaufstag. Sonntage sind als Einkaufstag gesperrt, weil die Läden zuhaben; an Feiertagen fragt die App nach, statt zu sperren — „teilweise eingeschränkt“ heißt eben nicht „geht nicht“. Am Sonntag erscheint gar kein Knopf, statt eines, der ohnehin nicht geht. Feiertage sind im Kalender an der farbigen Tageszahl zu erkennen und werden beim Namen genannt. Leere Slots bleiben leer — die früheren Hinweise („kein Frühstück zuhause“, „noch nichts vorgekocht“) sind bewusst entfernt worden: das waren Annahmen über eine bestimmte Person, keine Eigenschaften der App.

Gekocht- und Gegessen-Markierung: Jeder Eintrag lässt sich abhaken, beides einzeln und beides umkehrbar. Von Hand — die App leitet nichts daraus ab, dass ein Datum vergangen ist. In Phase 5 werden diese Haken zum Auslöser für den Vorrat: Kochen erzeugt einen Bestand, Essen baut ihn ab.

Zwei Ansichten: Der Kalender zeigt den ganzen Monat als Raster und darin nur die Beschriftungen — „Frühstück geplant“, „Mittagessen vorgeschlagen“, „Abendessen gekocht“, „Mittag nicht da“. Er ist die Startansicht und dient dem Überblick. Aufgebaut wie der Kalender auf dem Telefon: oben das Raster, das sich immer der Breite anpasst, darunter die Liste des gewählten Tages. Auf schmalen Displays stehen in den Zellen nur farbige Punkte — für Text ist dort kein Platz —, die Beschriftungen im Klartext stehen dann in der Liste darunter; ab mittlerer Breite stehen sie zusätzlich in den Zellen selbst. Ein Tippen wählt den Tag, „Tag bearbeiten“ springt in die Tagesansicht. Die Tagesansicht ist die ausführliche Wochendarstellung zum Bearbeiten und nennt jeden Tag mit Wochentag und Datum, heute/morgen/gestern zusätzlich als Marke. Wochen beginnen immer montags, nie sonntags — in beiden Ansichten und auch dann, wenn man mitten in der Woche einsteigt.

05

Plan, Automatik erledigt

Fertig: der Vorschlagsmotor, in zwei Betriebsarten. „Woche vorschlagen“ füllt in der Tagesansicht nur Leeres — Geplantes bleibt stehen, auch bei mehrfachem Start. Alles entsteht als Vorschlag, einzeln übernehmbar oder als ganze Woche verwerfbar; Bestätigtes und schon Abgehaktes bleibt beim Verwerfen verschont.

Ohne Gewohnheiten läuft eine schlichte Rotation: freie Mittag- und Abendslots bekommen ein Rezept, gekocht wird am selben Tag. Die Auswahl dreht sich durch die Sammlung — zuerst, was nie oder am längsten nicht geplant war, bei Gleichstand entscheidet die Bewertung; mittags und abends landet nie dasselbe Gericht. Bewusst ohne Annahmen darüber, wann jemand auswärts isst oder frühstückt.

Mit Gewohnheiten und API-Schlüssel liest die KI den Freitext aus den Einstellungen und verteilt danach: sie darf alle sechs Slots belegen, welche freilassen, Abwesenheiten setzen und Kochtermine vorziehen — etwa für Meal Prep, wenn der Text das so beschreibt. Sie bekommt dazu nur Tatsachen mit: Wochentag, Feiertag, der letzte Sonntag als mögliches Kochdatum. Was daraus folgt, steht allein im Gewohnheitstext. Die Antwort wird geprüft, nicht geglaubt: erfundene Rezepte, fremde Slots, Tage außerhalb der Woche und doppelt belegte Slots fliegen raus, ein Kochtermin nach dem Essenstermin wird zurechtgerückt, absurde Portionszahlen auf 1 gesetzt. Lieber ein Vorschlag weniger als ein kaputter Eintrag.

Ebenfalls fertig: Einplanen vom Rezept aus. Nach dem Anlegen eines Rezepts fragt die Rezeptansicht von selbst, ob es gleich eingeplant werden soll — diese oder nächste Woche, Mittag oder Abend. Belegte Slots sind nicht gesperrt, sondern austauschbar; im Knopf steht, was ersetzt würde. Gekocht wird am selben Tag; wer vorkochen will, verschiebt den Kochtermin danach im Plan. Über den Knopf „Einplanen“ ist das später jederzeit wieder erreichbar, auch für ältere Rezepte.

Fertig: der Vorrat, als vierte Hauptseite neben Rezepte, Plan und Einkaufsliste. Gezählt wird in Portionen — so gibt Sarah es an: „vier Portionen Reis eingefroren“. Andere Einheiten sind möglich, damit später auch der Vorratsschrank hineinpasst, aber die Portion ist der Normalfall. Posten sind nach Ort gruppiert (Gefrierschrank, Kühlschrank, Vorratsschrank), abgelaufene Haltbarkeitsdaten fallen farblich auf. Gleichartige Posten werden zusammengefasst: zweimal Reis mit gleichem Ort und Datum ergibt eine Zeile mit der Summe, keine zweite.

Wie der Vorrat wächst und schrumpft: An jedem als gekocht abgehakten Plan-Eintrag steht „einfrieren“ — Portionszahl angeben, fertig. Umgekehrt sinkt der Bestand von selbst, sobald eine Mahlzeit als gegessen abgehakt wird, die aus dem Vorrat kommt; nimmt man den Haken zurück, kommt er wieder. Doppeltes Abbuchen ist ausgeschlossen (plan_entry_stock.consumed_at merkt sich, was schon gebucht ist). Von Hand geht beides ebenfalls — kein Bestand stimmt ohne Nachpflege.

Mahlzeiten aus mehreren Vorratsposten. Ein Plan-Eintrag ist nicht mehr zwingend ein Rezept: „1 Portion Reis, 1 Portion Hackfleisch, 1 Portion Salsasoße aus dem Gefrierschrank“ sind drei Posten in einem Eintrag. Dafür gibt es die neue Tabelle plan_entry_stock; recipe_id bleibt daneben bestehen, beides zusammen ist erlaubt — etwa ein Rezept plus Reis als Beilage.

Fertig: Reste zuerst. Der Vorschlagsmotor verplant erst, was im Vorrat liegt, und lässt erst danach neu kochen — von den Resten zuerst das, was am ehesten abläuft. Schon verplante Portionen zählen mit: was in einer geplanten, aber noch nicht gegessenen Mahlzeit steckt, wird kein zweites Mal vorgeschlagen. Abgebucht wird trotzdem erst beim Gegessen-Haken, nicht beim Planen. In der KI-Betriebsart bekommt das Modell den Vorrat als Hinweis mit (inStock), darf ihn aber nicht selbst zuordnen — es soll solche Tage lieber freilassen, weil eine KI-Zuordnung nicht sauber verbucht würde.

Fertig: die Mengenskalierung. An jedem Plan-Eintrag mit Rezept steht „kochen“ und führt in den Kochmodus — mit der geplanten Portionszahl, nicht mit der Vorgabe des Rezepts. Wer vier Portionen einplant, sieht dort die Zutaten für vier. Gerundet wird auf Abmessbares (src/lib/portions.ts): aus 133,33 g werden 135 g, halbe Zahlen erscheinen als ½. Der Haken daneben heißt jetzt „als gekocht“ statt „kochen“ — er markiert, er kocht nicht.

Vorkochen auf Vorrat, wenn Tage ausfallen: Sarahs Fall — ist sie ein Wochenende weg, kommt sie nicht zum Kochen und hätte gern vorher eingefroren, was sie danach braucht. Die KI-Betriebsart bekommt dafür die Abwesenheiten der Woche und der Folgewoche mit und wird angewiesen, vor blockierten Tagen mehr Portionen einzuplanen. Die schlichte Rotation kann das nicht: Sie kocht am selben Tag und kennt keinen Kochrhythmus — wann jemand vorkocht, ist eine Gewohnheit und steht bewusst nicht im Code. Ohne Gewohnheitstext bleibt es also bei manuellem Vorkochen über den Kochtermin.

06

Einkaufsliste, Basis geplant

Automatische Generierung aus bestätigten Plan-Einträgen, Zusammenfassung gleicher Zutaten zu einem Posten, anteiliger Abzug beim Entfernen eines Rezepts, frei hinzufügbare manuelle Posten.

Was der Vorrat verschluckt, bleibt sichtbar: Zutaten, die nicht auf der Liste landen, weil sie laut Vorrat noch zuhause sind, verschwinden nicht stillschweigend. Sie stehen ausgegraut in einer zweiten Tabelle darunter, und ein Klick schiebt sie doch auf die Einkaufsliste — für den Fall, dass der Bestand nicht stimmt oder die Packung schon angebrochen ist. Das ist die Notbremse für einen Bestand, der nicht stimmt, und damit die Voraussetzung dafür, dem Vorrat überhaupt trauen zu können. Sinnvoll baubar, sobald der Vorrat aus Phase 5 steht.

07

Einkaufsliste, Feinschliff geplant

Abgleich mit dem Vorrat, Gruppierung nach Supermarktbereichen von Obst & Gemüse bis Tiefkühl, Bereich „zuletzt erledigt“ am Listenende, Haltbarkeitshinweise für einen möglichen zweiten Einkaufstermin.

Wann zwei Zutaten dieselbe sind

Grundlage für das Zusammenfassen in der Einkaufsliste, umgesetzt in api/lib/ingredients.php. Drei Regeln in dieser Reihenfolge: beschreibende Wörter fallen weg, gleichbedeutende Namen werden zusammengeführt, der Plural wird auf den Singular zurückgeführt.

DasselbeVerschieden
Zwiebeln = rote = weiße = große gelbe ZwiebelnZwiebeln ≠ Frühlingszwiebeln
Karotten = Möhren = MohrrübenZwiebeln ≠ Röstzwiebeln
Eier = große Eier = mittlere Eier = Bio-EierKarotten ≠ Karottensaft
Paprika = rote = grüne = gelbe PaprikaKartoffeln ≠ Süßkartoffeln
Sahne = Rahm = Schlagsahne = SchlagobersMilch ≠ Buttermilch

Die Unterscheidung trägt sich selbst: Beschreibende Wörter werden nur als eigenständiges Wort entfernt, an einem Wortanfang wird nie abgeschnitten. Deshalb bleibt jedes zusammengesetzte Wort eine eigene Zutat. Bewusst nicht entfernt werden Wörter, die das Produkt verändern — „gemahlen“ oder „gekocht“ machen aus Kaffeebohnen etwas anderes.

Dieselbe Unterscheidung gilt in der Suche: Bei Zutaten wird nur am Wortanfang gesucht, nie mitten im Wort. „Zwiebeln“ findet deshalb keine Frühlingszwiebeln. Beim Titel bleibt die Suche dagegen bewusst großzügig.

Wichtig bei Änderungen: Der Schlüssel wird beim Speichern eines Rezepts festgeschrieben. Wer die Regeln anpasst, muss anschließend npm run db:reindex ausführen, sonst tragen ältere Rezepte noch die alten Schlüssel.

Ideen & Backlog

Bewusst nicht im ersten Wurf

Sammelstelle für alles, was später kommen soll. Was du nebenbei erwähnst und nicht sofort umgesetzt haben willst, landet automatisch hier. vorgemerkt heißt: fest eingeplant, nur noch nicht dran. Backlog heißt: bewusst nach dem MVP.

Die drei Rezept-Punkte am Ende trugen bis eben die Markierung „Phase 3“ beziehungsweise „3b+“. Diese Phase ist abgeschlossen — sie sind also nicht vergessen worden, sondern bewusst nicht mitgelaufen. Sie stehen jetzt als Backlog und kämen in einem späteren Durchgang am Rezeptmodul dran, nicht zwischendurch.

Das Datenmodell ist auf die beiden Sharing-Punkte bereits vorbereitet — shared_with liegt an Recipe und ShoppingListItem und bleibt vorerst ungenutzt.

Rundgang durch die App Backlog

Eine Tour, die alle Funktionen erklärt und zeigt — nicht nur beim ersten Öffnen, sondern jederzeit wieder startbar, über ein eigenes Symbol neben den Einstellungen in der Kopfzeile.

Was den Zuschnitt bestimmt: Die App hat inzwischen vier Module, und vieles steckt in Feinheiten, die man von selbst nicht findet — dass Koch- und Essenstermin auseinanderfallen dürfen, dass je Slot mehrere Einträge möglich sind, dass eine Mahlzeit aus Vorratsposten bestehen kann, dass Gewohnheiten den Vorschlagsmotor steuern. Genau solche Stellen lohnen eine Tour; die Navigation erklärt sich von selbst.

Zu klären: Wo der Stand liegt. Ob jemand die Tour gesehen hat, gehört an den Nutzer in die Datenbank, nicht in den Browser-Speicher — sonst fängt sie auf dem Telefon wieder von vorn an. Woran die Schritte hängen. Eine Tour, die auf Bildschirmpositionen zeigt, zerbricht beim nächsten Umbau; robuster sind benannte Anker im Markup, die bewusst gepflegt werden. Womit sie etwas zeigt. Auf einem leeren Konto gibt es nichts vorzuführen — entweder die Tour erklärt dann nur, oder sie legt Beispieldaten an, die hinterher wieder verschwinden müssen. Und die Barrierefreiheit: Solche Touren sind mit Tastatur und Screenreader berüchtigt schlecht bedienbar, weil sie den Fokus an sich reißen. Das gehört von Anfang an mitgedacht, siehe den Punkt „Barrierefreiheit und DSGVO prüfen“.

Zeitpunkt: Sinnvoll erst, wenn die Funktionen stehen — eine Tour über eine Oberfläche, die sich noch ändert, muss bei jeder Änderung mitgepflegt werden. Nach Phase 7 also, und vor dem Livegang, falls außer Sarah noch jemand die App benutzen soll.

Anlässe planen: Weihnachten, Geburtstag, Besuch Backlog

Ein Festessen planen, nicht nur eine Mahlzeit. Sarahs Beispiel: an Weihnachten kommt die Familie mit zehn Personen, es gibt Suppe, Hauptgang, Nachtisch — vielleicht noch Vorspeise und Gebäck.

Das trifft das Datenmodell an einer Stelle, die bisher nirgends gebraucht wurde. Heute gilt: ein Eintrag ist ein Rezept in einem Slot. Ein Menü ist aber mehrere Rezepte, die zu einer Mahlzeit gehören, in einer Reihenfolge. Die Slots (Frühstück, Snack, Mittag, Snack, Abend, Sonstiges) bilden den Tagesablauf ab, keine Gänge — mehrere Einträge im Abendslot wären sie nur nebeneinander, nicht als Menü. Es bräuchte also eine Klammer darüber: einen Anlass mit Datum, Personenzahl und einer geordneten Liste von Gängen.

Was daran hängt: Die Mengenskalierung aus Phase 5 muss für zehn Personen tragen, nicht nur für zwei — und je Gang unterschiedlich, weil man von der Suppe weniger braucht als vom Hauptgang. Die Einkaufsliste sollte sich für so einen Anlass getrennt ausweisen lassen; der Wocheneinkauf und der Weihnachtseinkauf gehören nicht in eine Liste. Und die Gäste sind keine Nutzer der App: for_whom hält zwar freie Namen, aber „zehn Personen“ ist eher eine Zahl als eine Namensliste. Zum Punkt Haushalte ist das die Gegenrichtung — dort geht es um feste Mitesser, hier um einmaligen Besuch.

Schöner Anknüpfungspunkt: Die Feiertage kennt die App seit heute je Bundesland. Sie könnte also von sich aus fragen — „Weihnachten ist in drei Wochen, willst du planen?“ — statt darauf zu warten, dass jemand daran denkt. Auch der Kochtermin wird hier wichtiger als sonst: Vieles lässt sich Tage vorher vorbereiten, und genau dafür stehen Koch- und Essenstermin schon getrennt.

Zu klären: Ob ein Anlass eine eigene Tabelle wird oder eine Gruppierung über vorhandene Plan-Einträge. Ob Gänge eigene Slots bekommen oder eine Reihenfolge innerhalb eines Slots. Und ob sich ein gelungenes Menü als Ganzes speichern lässt, um es im nächsten Jahr wieder hervorzuholen — das wäre der eigentliche Gewinn, denn ein Weihnachtsessen plant man einmal im Jahr und erinnert sich nicht mehr.

Haushalte: mehrere Personen, ein Plan Backlog

Nutzer lassen sich in der Datenbank einem Haushalt zuordnen — Sarahs Beispiel: sie, Papa, Mama, Annika. Daraus folgt dreierlei:

1. Gemeinsame Einkaufsliste. Alle im Haushalt sehen dieselbe Liste und arbeiten daran, statt vier eigene zu führen. Das ist die größere Fassung des Backlog-Punkts „Einkaufslisten kombinieren“ und ersetzt ihn: dort ging es um zwei Nutzer, die ihre Listen auf Wunsch zusammenlegen, hier um einen dauerhaft geteilten Bestand. Die Tabelle shopping_list_contributions liegt bereits im Schema und hält fest, welcher Posten aus wessen Rezept stammt — genau das braucht es, wenn mehrere beitragen.

2. Für wen gekocht wird, wird zur echten Zuordnung. Beim Planen wählt man Personen aus dem Haushalt aus: „ich koche für Mama und mich“. Mama sieht daraufhin in ihrem eigenen Plan, dass jemand Rezept XY kocht, und muss dort selbst nichts eintragen. Das Feld for_whom an plan_entries gibt es schon, hält aber bislang nur freie Namen als JSON-Liste — es müsste auf echte Nutzerkennungen umgestellt werden. Ein Eintrag hätte dann einen Koch und mehrere Essende.

Auswählen lassen soll sich mehr als eine Person. Neben einzelnen Mitgliedern muss auch „der ganze Haushalt“ als Ganzes wählbar sein — wer für alle kocht, will nicht vier Namen einzeln anklicken. Das ist keine Abkürzung für „alle aktuellen Mitglieder“, sondern ein eigener Wert: Kommt jemand dazu, gilt der Eintrag auch für ihn.

4. Wer schon etwas geplant hat, ist sichtbar — ohne dass es sich ausschließt. Sarahs Beispiel: Sie trägt für Dienstagabend Pommes für sich ein. Mama will danach für den Haushalt kochen und sieht dabei, dass Sarah für sich schon etwas geplant hat. Sie kann Sarah trotzdem auswählen — danach steht bei beiden beides im Plan. Das ist wichtig: Der Hinweis warnt, er verbietet nicht. Zwei Einträge im selben Slot sind ohnehin erlaubt, das kann der Plan schon heute; neu wäre nur, dass man die Einträge der anderen überhaupt zu sehen bekommt.

5. Rezeptsammlung mit dem Haushalt teilen. Nicht nur einzelne Rezepte weiterreichen (das ist der Punkt „Rezepte teilen“), sondern die Sammlung gemeinsam führen: Was einer anlegt, sehen alle. Zu klären wäre, ob das alles-oder-nichts ist oder ob es private Rezepte daneben geben soll, und wer ein geteiltes Rezept ändern darf.

Die halbe Miete steht schon: Neben den Namen gibt es seit heute guest_count — eine Anzahl weiterer Personen ohne Namen, für Besuch. Die bleibt unverändert, wenn die Namen später zur Haushaltsauswahl werden: aus dem Freitextfeld wird eine Liste zum Anklicken, das Zahlenfeld daneben steht weiter für alle, die nicht zum Haushalt gehören. Deshalb war es sinnvoll, diese Hälfte vorzuziehen — sie hängt an keiner der offenen Fragen und muss später nicht umgebaut werden.

3. Rückkanal und Zustand. Wer mitisst, kann dem Koch einen Kommentar hinterlassen („ohne Mais“), der im Kochmodus sichtbar wird — dort wird er gebraucht, nicht in der Liste. Umgekehrt sehen die Mitessenden den Zustand: schon eingekauft, schon gekocht, eingefroren. Gekocht und gegessen werden bereits abgehakt; eingekauft und eingefroren wären neu — Einfrieren hängt am Vorrat aus Phase 5, und recipes.freezable sagt bisher nur, ob ein Rezept sich überhaupt einfrieren lässt.

Dazu sichtbar im Kopfbereich: „Personen in deinem Haushalt: …“, damit klar ist, mit wem man gerade plant.

Haushalte verwalten die Nutzer selbst — anlegen, jemanden dazuholen, wieder austreten, alles über die Oberfläche. Das steht nicht im Widerspruch zu „Kein Selbstanlegen von Konten“: Wer die App überhaupt benutzen darf, entscheidet weiterhin allein die Nutzertabelle, die Sarah pflegt. Wer einmal drin ist, darf sich aber frei mit anderen Berechtigten zusammentun. Einladen heißt also: eine vorhandene Person dazubitten, nie eine neue anlegen. Nötig wird dafür eine Einladung mit Zustimmung — ungefragt in einen fremden Haushalt gezogen zu werden, wäre ein Datenleck, weil damit Plan und Einkaufsliste offenliegen.

Zu klären: Was mit den Rezeptsammlungen geschieht: bleiben sie je Person getrennt (dann muss man ein Rezept teilen können, siehe „Rezepte teilen“) oder gehören sie dem Haushalt? Ebenso offen: Wer darf einen fremden Eintrag ändern oder löschen — nur der Koch oder alle? Und was passiert mit geteilten Einträgen, wenn jemand den Haushalt verlässt? Das ist der größte Einzelpunkt im Backlog und berührt fast jede Tabelle; sinnvoll erst nach Phase 7, wenn Plan und Einkaufsliste für eine Person stehen.

Kompletter Lebensmittelbestand zuhause Backlog

Nicht nur der Meal-Prep-Vorrat, sondern alles, was zuhause steht — Vorratsschrank, Kühlschrank, Gefriertruhe. Einmal erfasst, dann fortlaufend gepflegt: Einkäufe erhöhen den Bestand, Kochen zieht ab. Daraus ließe sich die Einkaufsliste um das kürzen, was ohnehin da ist, und Rezepte vorschlagen, die sich aus dem Vorhandenen kochen lassen.

Abgrenzung zur Vorratsübersicht aus Phase 5: Die ist bewusst klein — sie kennt nur, was aus einem Kochtermin übrig ist, und wird von den Gekocht-/Gegessen-Haken gefüllt. Dieser Punkt hier ist eine Stufe größer und braucht eine eigene Pflegeoberfläche. Die Tabelle stock_items liegt schon im Schema und könnte beides tragen; ob das sinnvoll ist oder ob es zwei getrennte Bestände braucht, ist offen.

Kassenzettel abfotografieren: Sarahs Vorschlag, wie der Bestand ohne Tipparbeit wieder aufgefüllt wird — Bon hochladen, die KI liest Posten und Mengen heraus und bucht sie ein. Der Weg über die KI ist bereits gebaut: der Rezept-Import nimmt schon Bilder und PDFs entgegen (api/routes/import.php, api/lib/claude.php), es bräuchte ein zweites Schema für Bons. Die Tücke liegt in den Kassenbons selbst: Artikelnamen sind abgekürzt und je Kette anders („BIO ZWIEBELN 500G“, „Zwiebel lose“), Mengen stehen mal als Stück, mal als Gewicht, mal nur als Preis. Die Zutaten-Normalisierung aus api/lib/ingredients.php hilft dabei, reicht aber nicht — eine Bestätigungsliste vor dem Einbuchen wird nötig sein. Unabhängig davon muss der Bestand immer auch von Hand pflegbar bleiben: nachtragen, korrigieren, wegwerfen. Der Bon ist die Abkürzung, nicht der einzige Weg.

Zu klären: Der Aufwand liegt nicht im Bauen, sondern im Pflegen — ein Bestand, der nicht stimmt, ist schlimmer als keiner. Wie kommen Einkäufe hinein, wenn gerade kein Bon da ist (etwa: erledigte Einkaufsliste bucht automatisch ein)? Wie wird abgezogen, wenn ein Rezept nur zum Teil gekocht wird? Wie geht die App mit angebrochenen Packungen und mit Haltbarkeit um? Sinnvoll wird das erst nach Phase 6/7, wenn die Einkaufsliste steht — die ist die natürliche Eingangstür für den Bestand.

Anbindung an einen echten Kalender Backlog

Eine Verbindung zum Kalender, damit sich Abwesenheiten von selbst übertragen: steht dort ein Termin über Mittag, wird der Mittagsslot im Plan automatisch als „nicht da“ markiert, statt dass Sarah es von Hand nachträgt. Denkbar über ein abonniertes ICS-Feed, das serverseitig gelesen wird — das passt zur Architektur, weil es kein Node braucht. Zu klären wären der Umfang (nur lesen oder auch schreiben), welche Termine überhaupt als Abwesenheit zählen, und wie das mit den Vorschlägen zusammenspielt.

Einkaufslisten kombinieren Backlog

Zwei Nutzer legen ihre Listen auf Wunsch zusammen, etwa für einen gemeinsamen Einkauf. Geht weitgehend in „Haushalte“ auf — dort teilen sich mehrere Personen dauerhaft eine Liste. Eigenständig bleibt dieser Punkt nur für den Fall, dass zwei Leute ohne gemeinsamen Haushalt einmalig zusammen einkaufen.

Rezepte teilen Backlog

Ein Rezept für andere Nutzer freigeben, statt es doppelt anzulegen.

KI-Freitextfeld im Plan Backlog

Eingaben wie „Ich bin Dienstag nicht da“ oder „diese Woche gerne Pasta“ werden interpretiert: Marker werden gesetzt, passende Rezepte vorgeschlagen.

Barrierefreiheit und DSGVO prüfen vor dem Livegang

Vor dem Livegang muss die App auf Barrierefreiheit und DSGVO-Konformität durchgesehen werden. Sarah hat das als Idee eingebracht; es steht hier bei den Punkten vor dem Livegang, weil es beides keine Kür ist.

Barrierefreiheit: Beim Bauen ist darauf schon geachtet worden — jedes Bedienelement hat eine Beschriftung, Zustände stehen in aria-pressed, der Kalender gibt je Tag einen vollständigen Vorlesetext, Farbe ist nie der einzige Träger einer Aussage (Vorschläge sind zusätzlich gestrichelt, Abwesenheit zusätzlich durchgestrichen). Geprüft ist es damit aber nicht. Nötig wären: Durchgang mit einer Tastatur allein, Test mit VoiceOver, Kontrastmessung in beiden Farbschemata, und ein Blick auf die Schriftgrößen — die kleinsten Beschriftungen im Kalender liegen bei 10 Pixeln, das ist unter dem Üblichen.

DSGVO: Zu klären sind Datenschutzerklärung und Impressum, die Rechtsgrundlage für die Verarbeitung, Auskunft und Löschung auf Anfrage, die Aufbewahrungsdauer, und die Auftragsverarbeitung durch Strato und Anthropic. Letzteres ist der heikelste Punkt: Beim KI-Import und beim Vorschlagen gehen Daten an einen Dritten — bei den Gewohnheiten sind das Angaben über die Lebensführung. Wer das nutzt, muss wissen, dass es passiert. Falls es mehrere Nutzer gibt, kommt die Trennung der Datenbestände dazu (die steht bereits) und, sobald es Haushalte gibt, die Frage, wer wessen Daten sehen darf.

Kein Selbstanlegen von Konten vor dem Livegang

Heute legt jeder eingegebene Name automatisch einen neuen Nutzer an. Das soll aufhören: Anmelden heißt nachschlagen, nie anlegen. Die vorhandene Tabelle users ist zugleich die Berechtigungsliste — wer dort nicht steht, kommt nicht rein. Gepflegt wird sie ausschließlich von Sarah direkt in der Datenbank (phpMyAdmin), nicht über die Oberfläche.

Umzusetzen: In api/routes/session.php den INSERT-Zweig entfernen und bei unbekanntem Namen mit 403 antworten. Die Felder closed_signup und allowed_names in api/config.php entfallen dabei — sie waren ein früherer, schwächerer Entwurf mit einer Namensliste in der Konfigurationsdatei. Wichtig: Auf einer frischen Instanz muss vorher mindestens ein Nutzer in der Tabelle stehen, sonst sperrt sich die App selbst aus. Lokal erledigt das npm run db:seed, live ein Eintrag über phpMyAdmin.

Zeitpunkt: Sarah hat entschieden, das erst vor dem Livegang umzusetzen. Während der Entwicklung bleibt das Anlegen über die Oberfläche möglich, was beim Bauen der Rezept-Module praktisch ist.

Spam- und Zugriffsschutz vor dem Livegang

Damit Unbefugte die öffentlich erreichbare Adresse nicht einfach durchprobieren können: Begrenzung der Anmeldeversuche pro Adresse und eine zusätzliche Hürde vor der Namensabfrage. Lässt sich erst in der Live-Umgebung sinnvoll bauen und prüfen.

Fertiger Ordner für den Live-Server zum Schluss

Am Ende legt Claude einen Ordner auf den Schreibtisch, der alles enthält, was auf den Live-Server hochgeladen wird. Wichtig dabei: MealMap ist kein PHP-Projekt, sondern braucht Node auf dem Server – siehe offener Punkt weiter unten.

Änderungswünsche in beliebiger Sprache Backlog

Der Ändern-Knopf versteht heute feste Muster („2 statt 3 Eier“, „ohne Zwiebeln“, „Butter durch Öl ersetzen“). Mit hinterlegtem API-Schlüssel soll er beliebige Sätze verstehen — etwa „mach das Ganze vegan“ oder „halbiere alle Mengen außer den Gewürzen“. Die zweistufige Bedienung bleibt: erst zeigen, was verstanden wurde, dann schreiben.

Zutatenfilter mit Auswahlliste Backlog

Statt nur über das Freitextfeld soll sich aus einer Liste der vorhandenen Zutaten auswählen lassen, welche enthalten sein müssen — mehrere gleichzeitig, alle müssen zutreffen. Die Liste speist sich aus den Zutaten der eigenen Sammlung, zusammengefasst über den vereinheitlichten Schlüssel (Zwiebeln und rote Zwiebeln erscheinen als ein Eintrag).

Ähnliche Treffer statt leerer Liste Backlog

Findet der Zutatenfilter nichts, soll nicht nur „keine Treffer“ dastehen. Stattdessen: fast passende Rezepte mit dem Hinweis, was fehlt („enthält 2 von 3 — es fehlt Mais“), und Rezepte, die sich passend machen ließen.

Wichtig dabei: Eine solche Änderung gilt nur für dieses eine Mal und wird nicht in die Sammlung geschrieben — außer Sarah sagt ausdrücklich, dass sie dauerhaft übernommen werden soll. Es braucht also zwei getrennte Wege: eine flüchtige Variante fürs Kochen und die vorhandene dauerhafte Änderung über den Ändern-Knopf.

Platz für neue Ideen

Alles, was dir während der Umsetzung einfällt, kommt hier rein — einmal erwähnen reicht, ich trage es nach und veröffentliche das Dossier neu.

Offene Punkte

Zu klären, bevor die jeweilige Phase startet

API-Key liegt im Klartext vor Livegang

Der Key wird serverseitig am Nutzer gespeichert, sonst könnte der Server die Imports nicht ausführen. In der lokalen MySQL-Datenbank ist das unkritisch. Sobald die App online geht, sollte er verschlüsselt abgelegt werden.

npm audit meldet postcss Entscheidung offen

Next 15.5.25 bringt intern eine postcss-Version mit, für die Sicherheitshinweise vorliegen. Betroffen ist die Build-Kette, nicht die laufende App; lokal ist das unkritisch. Bereinigen ließe es sich nur durch den Sprung auf Next 16 — ein Hauptversionswechsel, den ich nicht ungefragt mache. Spätestens vor dem Livegang entscheiden.

Einheiten ohne saubere Umrechnung Phase 6

„2 Zwiebeln“ und „150 g Zwiebeln“ lassen sich nicht addieren. Die Liste fasst nur zusammen, was dieselbe Einheit hat, und zeigt den Rest als getrennte Posten. Erfahrungsgemäß der Punkt, an dem eine Einkaufsliste unübersichtlich wird.

Haltbarkeitsdaten kommen nicht von allein Phase 7

Für den Hinweis auf einen zweiten Einkaufstermin braucht es pro Zutat eine grobe Haltbarkeit. Ich starte mit einer hinterlegten Liste für gängige Zutaten, die du überschreiben kannst.

MealMap braucht MAMP nicht: Next.js bringt seinen eigenen Server mit und läuft über Node auf Port 3000, Apache und MySQL bleiben davon unberührt. Weil der Projektordner im DocumentRoot liegt, wäre er theoretisch auch über localhost:8888/MealMap erreichbar — dort käme allerdings nur der nackte Quellcode heraus, nicht die App. MAMP kann also weiterlaufen, sollte aber nicht als Einstieg benutzt werden.

Einrichtung

Auf einem neuen Rechner starten

Projekt aus Git holen, in den Ordner wechseln, dann diese drei Zeilen — mehr ist nicht nötig:

npm install
cp api/config.example.php api/config.php   # Zugangsdaten der Datenbank
npm run db:migrate  # Tabellen in MySQL anlegen
npm run db:seed     # optional: Beispieldaten
npm run preview     # http://localhost:8888/MealMap/

Der Ordner uploads/ muss beschreibbar sein — er nimmt Bilder und PDFs auf. Voraussetzung ist ein laufender MAMP (Apache und MySQL) sowie eine Datenbank namens mealmap. Die .env und api/config.php liegen bewusst nicht im Repo, weil sie Zugangsdaten enthalten — beide haben eine Vorlage daneben.

Befehle

Was du im Projektordner ausführen kannst

BefehlWas passiert
npm run devStartet Next.js auf localhost:3000. Der normale Weg beim Entwickeln.
npm run syncStartet Next plus BrowserSync auf localhost:3001. Gibt zusätzlich eine Netzwerk-URL aus, mit der du die App am Handy öffnest; Scrollen und Klicken laufen dann auf allen Geräten synchron.
npm installInstalliert die Pakete. Auf einem frischen Rechner danach cp api/config.example.php api/config.php, npm run db:migrate und npm run preview.
npm run previewBaut dist/ für den Unterordner /MealMap, mit den lokalen Zugangsdaten. Danach läuft die App unter localhost:8888/MealMap/. Nach jeder Änderung neu ausführen.
npm run watchBeobachtet src/, api/ und public/ und baut das Bündel bei jeder Änderung neu. Die Seite im Browser danach einmal neu laden.
npm run db:reindexBerechnet die Zutatenschlüssel aller Rezepte neu. Nötig, wenn die Regeln in api/lib/ingredients.php geändert wurden.
npm run bundleBaut dist/ ohne Zugangsdaten — das ist der Ordner, der auf den Server geht.
npm run iconsErzeugt Logo-PNG, Favicon und Homescreen-Icon neu aus assets/logo-mark.svg. Nur nötig, wenn du die Bildmarke änderst.
npm run buildProduktions-Build, prüft zugleich Typen und Lint-Regeln.
npm run db:migrateLegt die Tabellen in MySQL an, aus api/schema.sql. Live stattdessen die Datei über phpMyAdmin einspielen.
npm run db:seedFüllt Beispieldaten ein. Bewusst getrennt vom Schema, damit die Live-Instanz leer startet.

Arbeitsregeln

Für die Zusammenarbeit

  • Git bleibt bei Sarah. Claude führt keine Git- oder GitHub-Befehle aus — auch keine lesenden wie status oder log. Wenn etwas versioniert werden soll, gibt Claude nur Bescheid, was zu tun ist, und schlägt auf Wunsch eine Commit-Nachricht vor. Ausnahme: die .gitignore darf als Datei angelegt und gepflegt werden.
  • Rückfragen in Abfrageform. Offene Fragen kommen als Auswahl mit erklärten Antwortmöglichkeiten, nicht als Fließtext. Routinemäßige Kleinigkeiten entscheidet Claude selbst und sagt kurz Bescheid.
  • Diese beiden Regeln gelten projektübergreifend. Sie stehen in ~/.claude/CLAUDE.md und werden in jeder Claude-Code-Sitzung geladen, unabhängig vom Projektordner.
  • Phase für Phase. Nach jeder Phase wird gestoppt und auf Freigabe gewartet, bevor es weitergeht.
  • Aufträge werden erst auf den Zeitpunkt geprüft. Vor dem Bauen schätzt Claude ein, ob die Umsetzung jetzt schon sinnvoll ist. Wenn nein, wird sie nicht gebaut, sondern hier im Dossier vermerkt – mit Begründung, wann sie fällig wird.
  • Immer ein vollständiges Rezept zum Testen. Nach jedem Aufräumen muss mindestens ein Rezept mit Zutaten, Schritten, Kategorien und Bewertung in der Datenbank stehen — sonst sind Liste, Kochmodus, Filter und Plan nicht ansehbar. Zur Not npm run db:seed.
  • Keine Testdaten in Migrationen. Beispieldaten entstehen nur über npm run db:seed, damit die Live-Datenbank leer startet.
  • Dieses Dossier wird mitgeführt. Entscheidungen, Ideen und offene Punkte kommen hier rein, damit nichts im Chatverlauf verschwindet.
